# Что такое инвариант

Инвариант — это условие, которое **должно оставаться истинным** в определённый момент времени независимо от того, какие операции выполняет программа.

Интуитивно:

* система может менять состояние;
* данные могут проходить через множество функций;
* объекты могут мутировать;
* потоки могут работать параллельно;

но некоторые свойства обязаны сохраняться всегда.

Например:

* баланс счёта не может стать отрицательным;
* очередь не должна терять сообщения;
* `len(slice)` не может быть отрицательным;
* заказ не может быть одновременно `paid` и `cancelled`.

Инварианты — это фундамент корректности программы.
Они определяют:

* что считается «валидным состоянием» системы;
* какие переходы допустимы;
* где система сломана.

---

## Инвариант состояния объекта

Это условие, которое всегда должно выполняться для объекта после его создания и после завершения публичных операций.

Пример: банковский счёт.

```go
type Account struct {
	id      string
	balance int64
}
```

Инварианты:

* `balance >= 0`
* `id != ""`

Если объект оказался в состоянии:

```go
Account{
    id: "",
    balance: -100,
}
```

то объект повреждён логически, даже если код компилируется.

---

## Пример инварианта структуры данных

```go
type Stack struct {
	items []int
	size  int
}
```

Инвариант:

```text
size == len(items)
```

Если:

```go
s.size = 10
len(s.items) == 9
```

структура данных повреждена.

---

## Проверка инварианта

```go
func (s *Stack) validate() {
	if s.size != len(s.items) {
		panic("stack invariant violated")
	}
}
```

---

## Инвариант цикла

Инвариант цикла — условие, которое:

* истинно до начала итерации;
* остаётся истинным после каждой итерации;
* помогает доказать корректность алгоритма.

Классический пример: поиск максимума.

```go
func Max(arr []int) int {
	max := arr[0]

	for i := 1; i < len(arr); i++ {
		if arr[i] > max {
			max = arr[i]
		}
	}

	return max
}
```

Инвариант цикла:

```text
После i-й итерации max содержит максимум элементов arr[0:i]
```

Именно через инвариант обычно доказывают корректность алгоритмов.

---

## Инварианты и корректность программы

Корректность программы часто формулируется как:

```text
если предусловия выполнены,
то программа сохраняет инварианты
и гарантирует постусловия
```

---

## Предусловие vs инвариант vs постусловие

## Предусловие

Что должно быть истинно до вызова функции.

```go
func Withdraw(amount int64)
```

Предусловие:

```text
amount > 0
```

---

## Инвариант

Что всегда должно оставаться истинным.

```text
balance >= 0
```

---

## Постусловие

Что гарантируется после выполнения функции.

```text
новый баланс = старый баланс - amount
```

---

## Пример бизнес-инварианта

```go
type OrderStatus string

const (
	StatusNew       OrderStatus = "new"
	StatusPaid      OrderStatus = "paid"
	StatusCancelled OrderStatus = "cancelled"
)
```

Инвариант:

```text
заказ не может быть одновременно paid и cancelled
```

Плохая модель:

```go
type Order struct {
	Paid     bool
	Cancelled bool
}
```

Потому что состояние:

```go
Paid=true
Cancelled=true
```

логически невозможно.

Лучше:

```go
type Order struct {
	Status OrderStatus
}
```

Модель сама ограничивает пространство состояний.

Это важная идея:

> Хороший дизайн уменьшает количество невозможных состояний.

---

## Инварианты в транзакциях

Очень часто инварианты существуют на уровне нескольких записей.

Пример перевода денег.

Инвариант:

```text
общая сумма денег в системе не меняется
```

---

## Корректная транзакция

```go
tx, err := db.BeginTx(ctx, nil)
if err != nil {
	return err
}

_, err = tx.Exec(`
    UPDATE accounts
    SET balance = balance - $1
    WHERE id = $2
`, amount, fromID)

if err != nil {
	tx.Rollback()
	return err
}

_, err = tx.Exec(`
    UPDATE accounts
    SET balance = balance + $1
    WHERE id = $2
`, amount, toID)

if err != nil {
	tx.Rollback()
	return err
}

return tx.Commit()
```

Транзакция защищает инвариант:

```text
деньги не могут исчезнуть или появиться
```

---

## Пример нарушения инварианта

Без транзакции:

```go
withdraw()
panic("crash")
deposit()
```

Деньги исчезли.

Инвариант разрушен.

---

## Инварианты в многопоточности

В concurrent-системах инварианты становятся сложнее, потому что состояние меняется одновременно.

Пример:

```go
type Counter struct {
	value int
}
```

Инвариант:

```text
каждый increment увеличивает значение ровно на 1
```

Но:

```go
c.value++
```

не атомарен.

Возможен lost update.

---

## Нарушение инварианта

Два потока:

```text
read 5
read 5
write 6
write 6
```

Ожидалось:

```text
7
```

Получили:

```text
6
```

Инвариант:

```text
количество increment == value
```

разрушен.

---

## Как защищают инварианты в concurrency

* mutex
* atomic operations
* actor model
* immutability
* serial execution
* transactional memory
* optimistic locking

---

## Инварианты в distributed systems

В распределённых системах инварианты особенно сложны, потому что:

* нет общего memory space;
* есть network partitions;
* есть retry;
* есть eventual consistency;
* сообщения могут дублироваться.

---

## Пример: exactly-once

Инвариант:

```text
платёж должен быть проведён ровно один раз
```

Но Kafka/SQS/RabbitMQ могут доставить сообщение повторно.

Поэтому нужен:

* idempotency key;
* deduplication;
* transactional outbox;
* inbox pattern.

---

## Инварианты в очередях сообщений

Пример инварианта:

```text
сообщение либо обработано,
либо может быть обработано повторно
```

Нельзя:

```text
сообщение потеряно и не обработано
```

Поэтому acknowledgement делают после commit.

---

## Инварианты в базах данных

БД — огромный механизм поддержания инвариантов.

Примеры:

* PRIMARY KEY
* UNIQUE
* FOREIGN KEY
* CHECK
* NOT NULL

---

## CHECK constraint

```sql
CHECK (balance >= 0)
```

База сама защищает инвариант.

Это важная идея:

> Инварианты лучше защищать на самом нижнем уровне системы.

---

## Aggregate invariants в DDD

В Domain-Driven Design aggregate — граница консистентности.

Aggregate root отвечает за сохранение инвариантов.

Пример:

```text
Order:
- totalPrice == sum(items)
- paid order нельзя менять
- quantity > 0
```

Именно поэтому изменение aggregate обычно делают через методы:

```go
order.AddItem()
order.Pay()
```

а не через прямую мутацию полей.

---

## Почему panic иногда используют для защиты инвариантов

`panic` обычно используют не для пользовательских ошибок, а для:

* невозможных состояний;
* нарушения внутренних гарантий;
* corruption;
* programmer bugs.

Пример:

```go
func (s *Stack) Pop() int {
	if len(s.items) == 0 {
		panic("empty stack")
	}
}
```

Или:

```go
func (s *Stack) validate() {
	if s.size != len(s.items) {
		panic("corrupted stack")
	}
}
```

Идея:

```text
если нарушен внутренний инвариант —
система больше не заслуживает доверия
```

Это уже не recoverable business error.

---

## Как формулируют инварианты

Хороший инвариант:

* точный;
* проверяемый;
* локальный;
* не двусмысленный;
* относится к состоянию системы.

Плохой:

```text
система должна работать быстро
```

Хороший:

```text
balance никогда не отрицателен
```

Проверяется:

```text

```

```text

balance >= 0
```

## Типичные ошибки понимания инвариантов

## 1. Путать инвариант с бизнес-правилом

Не каждое правило — инвариант.

```text
скидка 10% по пятницам
```

— это правило.

А:

```text
сумма заказа >= 0
```

— инвариант.

---

## 2. Слишком слабые инварианты

```text
данные должны быть валидными
```

Непроверяемо.

---

## 3. Слишком глобальные инварианты

Чем глобальнее инвариант — тем сложнее его поддерживать.

---

## 4. Надеяться только на application layer

Если инвариант критичен:

* дублируют проверки;
* используют constraints;
* используют transactional guarantees.

---

## 5. Игнорировать concurrency

Код может сохранять инвариант в single-threaded execution и нарушать его под race condition.

---

## Признаки хорошего инварианта

Хороший инвариант:

* формален;
* проверяем;
* локализован;
* стабилен;
* не зависит от UI;
* помогает отсекать невозможные состояния;
* может быть автоматически проверен.

---

## Как мышление через инварианты помогает проектировать backend-системы

Это один из самых сильных способов проектирования.

Вместо вопроса:

```text
как реализовать feature?
```

задают вопрос:

```text
какие свойства системы никогда нельзя нарушать?
```

Это меняет архитектуру.

---

## Пример

Не:

```text
как сделать платежи?
```

А:

```text
как гарантировать что деньги не исчезнут?
```

Тогда появляются:

* транзакции;
* outbox pattern;
* idempotency;
* retries;
* locks;
* consistency boundaries.

---

## Ключевая идея

Инварианты — это не «дополнительная проверка».

Они являются:

* фундаментом корректности;
* описанием допустимых состояний системы;
* границами консистентности;
* основой concurrency safety;
* основой transactional integrity;
* способом проектирования domain model.

Сильные backend-системы обычно строятся вокруг явно сформулированных инвариантов.
